> **Purpose of this file:** This is the source-of-truth implementation brief for building Autumn's second Design Engineer take-home assignment. The goal is to redesign it around what an independent hotel owner actually needs to understand, while proving that the product is backed by a real hosted database and realistic data.

> 1. The assignment constraints in this document
> 2. The product hierarchy and user needs in this document

# 1. Assignment Summary

Autumn helps independent hotels understand whether Autumn's marketing work is producing more **direct bookings** and **direct booking revenue**.

The existing marketing dashboard contains useful information, but it is dense and technical. It treats impressions, clicks, CTR, bookings, devices, traffic, markets, events, page views, and revenue as similarly important. That may work for a growth marketer, but Autumn's customer is usually not a growth marketer.

The assignment is to design and build **two connected, deployed screens**:

1. **Main Marketing Dashboard**
   - The executive-level view.
   - The first screen a hotel owner should see.
   - Must quickly answer: **"Is Autumn helping my hotel get more direct bookings and revenue?"**

2. **Booking Performance Detail Screen**
   - A natural drill-down from the main dashboard.
   - Working title: **"What's Driving Your Bookings"**
   - Explains where the bookings and revenue came from without crowding the first screen.

Both screens must be:
- Built in React + Next.js.
- Connected to a real hosted database.
- Backed by at least 720 days of plausible, meaningful marketing data.
- Live and deployed.
- Connected with clear navigation.
- Responsive, polished, and maintainable.

The final submission must include:
- One live URL with both screens reachable.
- Repository link.
- Setup/database/seeding instructions.
- Screenshots of:
  - the old/reference dashboard,
  - redesigned main screen,
  - connected detail screen.

# 2. Non-Negotiable Constraints

## 2.1 ABSOLUTELY NO HARDCODED DASHBOARD DATA

This is the most important engineering constraint.

The assignment explicitly says a hardcoded dashboard will not pass.

### Do NOT do this

```ts
const revenue = 18685;
const bookings = 39;
const impressions = 6001;
const websiteVisits = 1006;

const insights = [
  {
    title: "Chicago is your strongest market",
    value: "$4,778"
  }
];
```

Do not place demo metrics, chart arrays, market rankings, campaign performance numbers, growth percentages, hotel-specific insights, or other business-state values directly in React components.

Do not simply create a database row such as:

```text
dashboard_metrics
revenue = 18685
bookings = 39
impressions = 6001
```

and use the database as a storage wrapper for a fake static dashboard. The data model should contain believable underlying facts that are aggregated into the dashboard.

### What MAY be hardcoded in application code

UI structure and product language are allowed to live in code:

- `"Direct booking revenue"`
- `"Website visits"`
- `"Compared with the same period last year"`
- Date-range option labels
- Tooltip definitions
- Component layout
- Chart configuration
- Thresholds/rules used to generate insights
- Formatting logic

### What MUST come from the database or be derived from database values

- Property name/details
- Revenue
- Booking counts
- Impressions
- Ad clicks
- Website visits
- CTR
- Booking conversion
- Average booking value
- Current-vs-comparison changes
- All chart series
- Campaign rankings
- Feeder market rankings
- Market revenue
- Campaign revenue
- Campaign bookings
- Insight values and entities
- Autumn action/activity records
- "Last updated" data date

### Hardcoding test

Before submission:

1. Search the codebase for visible demo numbers.
2. Change a booking value in Supabase.
3. Refresh the app.
4. Confirm the headline revenue, average booking value, relevant chart values, and dependent insight(s) update automatically.
5. Change the selected date range.
6. Confirm all relevant metrics recalculate.
7. Temporarily return no records and verify a legitimate empty state appears rather than fallback demo data.

If modifying the underlying database does not change the product, the implementation is wrong.

---

## 2.2 Use a Real Hosted Database

Preferred implementation:

- **Supabase hosted Postgres**

Why:
- Fast to build within 24 hours.
- Relational data fits campaigns, daily metrics, bookings, markets, and property relationships well.
- Easy to seed.
- Easy to query from Next.js.
- Easy to deploy with Vercel.
- Supports RLS if public/demo read access is needed.

The dashboard must fetch data at runtime from the hosted database.

A local JSON file, TypeScript array, local-only SQLite database, static CSV, or hardcoded chart series does **not** satisfy the requirement.

---

## 2.3 Seed at Least 720 Days

Seed **at least 760 days** to leave a buffer above the requirement.

The data must not be random visual noise.

It must support believable:
- seasonality,
- year-over-year comparison,
- campaign performance,
- feeder markets,
- direct bookings,
- booking revenue,
- changes in conversion,
- realistic insights.

Use a deterministic seeded random generator so the dataset is repeatable.

---

## 2.4 Two Screens Only as the Core Product

Do not spend time building unrelated settings, authentication flows, billing, hotel setup, messaging, or an admin panel.

Required routes:

```text
/dashboard
/dashboard/bookings
```

Optional query parameters are encouraged:

```text
/dashboard?range=ytd
/dashboard/bookings?range=ytd
```

or explicit dates:

```text
/dashboard?from=2026-01-01&to=2026-09-05
```

The detail screen must feel like the answer to a question raised on the main screen, not a random second page.

---

## 2.5 Deployment Is Part of Done

The app is not done until:
- It builds successfully.
- It is deployed on Vercel.
- Production environment variables are configured.
- Production can query Supabase.
- Both routes work directly when opened.
- Refreshing a nested route does not fail.
- No credentials are committed.
- The live app has no obvious console errors.

# 3. Product Thesis

The dashboard should feel like:

> **A 30-second briefing from a trusted hotel marketing operator, not an ad platform that asks the hotel owner to become a marketer.**

Autumn's customer should not have to interpret a wall of analytics.

The product should answer these questions in this order:

1. **What did Autumn produce for me?**
2. **Is performance getting better or worse?**
3. **How did guests get from seeing Autumn's marketing to booking?**
4. **What changed?**
5. **Is anything concerning?**
6. **What is Autumn doing about it?**
7. **If I want more detail, what is driving the bookings?**

This hierarchy is the main product decision.

---

# 4. Who We Are Designing For

## Primary user

An owner/operator or general manager of an independent:
- hotel,
- inn,
- B&B,
- ranch,
- lodge,
- boutique property.

This person may simultaneously handle:
- front desk responsibilities,
- revenue decisions,
- guest issues,
- vendor relationships,
- staffing,
- property maintenance,
- marketing oversight.

They are busy. They are not necessarily a marketer.

They care about business outcomes, not marketing vocabulary.

### Their mental model

They naturally ask:

- Did Autumn bring me more direct bookings?
- How much revenue did those bookings create?
- Is that better than last year?
- Where are these guests coming from?
- What changed recently?
- Is something going wrong?
- What is Autumn doing about it?

They do **not** naturally wake up asking:

- What is my CTR?
- What is my CVR?
- How many session starts did I record?
- What was my device split?
- What was my pages-per-session metric?

Those metrics may still be useful, but they should be subordinate to outcomes.

# 5. UX and Copy Principles

## 5.1 Outcome first, explanation second

The first visual priority is:

1. Direct booking revenue
2. Direct bookings
3. Change versus a meaningful comparison period

Everything else explains those outcomes.

Do not give impressions the same visual weight as revenue.

---

## 5.2 Translate marketing language into plain English

Preferred labels:

| Technical term | Primary user-facing language |
|---|---|
| Impressions | Ad appearances / times your hotel was seen |
| Clicks | Ad clicks |
| Website sessions from ads | Website visits from Autumn ads |
| CTR | Click-through rate, shown as secondary explanation |
| CVR | Booking rate / visitor-to-booking rate |
| Attribution | "Bookings Autumn can connect to its marketing" |
| Feeder market | Where booking guests are coming from |
| Campaign performance | What's driving your bookings |

If a technical term is useful, spell it out and explain it. Do not use acronym-only labels such as `CTR` or `CVR` as primary copy.

---

## 5.3 Progressive disclosure

The main dashboard should show only what a busy owner frequently needs.

Secondary marketing details belong:
- on the detail screen,
- in tooltips,
- in expandable content,
- or in context-sensitive insights.

Do not permanently show a metric simply because the database contains it.

---

## 5.4 Do not celebrate vanity metrics as business wins

Bad:

> "You passed 10,000 impressions!"

Better:

> "Direct booking revenue is up 18% compared with the same period last year."

Impressions matter because they help explain the path to bookings. They are not the final outcome.

---

## 5.5 Show both good news and genuine issues

The product should not feel like a marketing agency congratulating itself.

Examples:

Positive:
> "Direct booking revenue is up 18% versus the same period last year."

Diagnostic:
> "Website visits increased 22%, but the booking rate fell from 4.1% to 3.2%."

Opportunity:
> "Chicago is your fastest-growing booking market."

Calm/stable:
> "Performance is steady. Booking revenue is within 3% of the same period last year."

This creates trust.

---

## 5.6 Calm, hospitality-native visual tone

The dashboard should feel:
- warm,
- calm,
- premium,
- approachable,
- confident,
- hospitality-oriented.

It should **not** feel:
- like Google Ads,
- like a dense BI tool,
- like a crypto dashboard,
- overly neon,
- aggressively "AI",
- overly decorative,
- covered in gradients and chart colors.

Suggested direction:
- warm off-white / very light neutral canvas,
- charcoal/dark text,
- muted brand accent (teal is consistent with the current Autumn surface),
- soft borders,
- light shadows only where necessary,
- generous whitespace,
- 12–16px radius,
- large outcome typography,
- very restrained chart palette,
- clear hierarchy rather than many colored KPI tiles.

Do not turn "Autumn" into a literal fall-leaf theme.

# 7. Screen 1 Requirements — Main Dashboard

## 7.1 Header

Include:
- Property name fetched from database.
- Page title: `Marketing` or `Marketing Performance`.
- Date-range selector.
- Small "Data through {date}" or "Updated {date}" indicator.

Recommended ranges:
- Last 30 days
- Last 90 days
- Year to date
- Last 12 months

Optional:
- Custom range, only if easy to implement without sacrificing polish.

Default:
- **Year to date**

For hotel seasonality, comparison copy should default to:
- **"vs same period last year"**

All date selection must change the actual queries and derived results.

---

## 7.2 Executive Performance Hero

This is the most important component.

Example structure, but values must come from the database:

```text
Your direct bookings are growing

$XX,XXX
Direct booking revenue from Autumn

XX direct bookings
↑ XX% vs same period last year

$XXX average booking value
```

Hierarchy:
- Revenue is largest.
- Booking count is second.
- Comparison is prominent but secondary.
- Average booking value is useful supporting context, not another giant KPI card.

Do not repeat the same booking revenue in multiple cards.

### Status sentence

Generate the sentence from data.

Examples:
- `Your direct bookings are growing`
- `You're having a strong season`
- `Direct booking performance is steady`
- `Traffic is growing, but fewer visitors are booking`

Do not hardcode a hotel-specific status.

A reusable rule/template may be coded, but the result must be driven by queried metrics.

---

## 7.3 Combined Guest Journey / Tracker

This replaces separate equally weighted cards for impressions and website visits.

Primary stages:

```text
Ad appearances
      ↓
Website visits
      ↓
Direct bookings
      ↓
Booking revenue
```

Desktop may use a horizontal layout.

Example:

```text
6,001                 1,006                 39                  $18,685
Ad appearances   →    Website visits   →    Direct bookings →   Revenue
       17% click-through         3.9% visitor-to-booking
```

Again: these are illustrative values only. Never hardcode them.

Recommended behavior:
- `impressions` = sum of campaign daily metrics
- `clicks` = sum of campaign daily metrics
- `website visits` = sum of campaign daily metrics
- `CTR` = clicks / impressions
- `visitor-to-booking rate` = attributed bookings / website visits
- `revenue` = sum of attributed booking values

Keep CTR visually secondary. The owner should understand the journey even if they ignore CTR.

Potential tooltips:
- **Ad appearances:** "How many times your hotel's Autumn ads were shown."
- **Click-through rate:** "The share of ad appearances that led to an ad click."
- **Booking rate:** "The share of Autumn-driven website visits that became direct bookings."

Do not create a literal funnel cone. A calm linear journey is easier to scan.

---

## 7.4 Direct Booking Performance Trend

Keep one primary chart.

Title:
- `Direct booking performance`

Controls:
- `Revenue`
- `Bookings`

Prefer a toggle instead of plotting many metrics on multiple axes.

Comparison:
- current selected period,
- same period last year.

Aggregation:
- <= 45-day range: daily
- 46–180 days: weekly
- > 180 days: monthly

The chart should answer:

> "Are direct bookings/revenue trending in the right direction?"

Do not show four noisy lines for impressions, traffic, clicks, and bookings on the main chart.

Requirements:
- tooltip with date + value,
- clear legend/comparison,
- empty state,
- no misleading interpolation,
- responsive width.

---

## 7.5 "What Changed" Insights

Show a maximum of approximately 3 insight cards.

These should be calculated from queried data.

Possible rule hierarchy:

### Concern rules — highest priority

Example:
- Website visits up >= 15% YoY AND booking conversion down >= 10% relative:
  - `More travelers are visiting, but fewer are booking`
  - Show the actual current and comparison conversion values.

- Revenue down >= 10%:
  - `Direct booking revenue is down from last year`
  - Show amount/percentage.

### Positive rules

- Revenue up >= 10%:
  - `Direct booking revenue is up {x}%`
- Bookings up >= 10%:
  - `{n} more direct bookings than the same period last year`
- A feeder market grows materially:
  - `{market} is your fastest-growing market`
- One campaign drives a meaningful share of booking revenue:
  - `{campaign} is driving the most booking revenue`

### Stable rule

If nothing crosses meaningful thresholds:
- `Performance is steady`
- Explain that current booking revenue is close to the comparison period.

Important:
- Templates may live in code.
- Market names, values, percentages, and rankings must come from DB queries.
- Avoid pretending an insight is AI-generated unless it actually is.

---

## 7.6 "What Autumn Is Doing"

This is a small but strategically important section.

The customer asks: **"What is Autumn doing about it?"**

Show 2–3 recent/current actions fetched from `autumn_actions`.

Example structure:

```text
What Autumn is working on

Growing Chicago demand
Chicago is converting strongly, so campaign emphasis increased in this market.
Adjusted Aug 28

Protecting high-intent searches
Brand Protection remains the strongest booking driver.
Active
```

This should make Autumn feel like an active operator, not a passive reporting tool.

Requirements:
- records stored in database,
- action date,
- status,
- optional associated campaign,
- short plain-language explanation.

Do not build an action editor/admin workflow.

---

The main outcome card or a clear supporting CTA should link naturally to:

`/dashboard/bookings`

Recommended copy:

- `See what's driving bookings →`
- `Explore booking performance →`

The user should immediately understand what they will find after clicking.

## 10.1 Recommended Database

Use:

Use approximately these tables:

## 10.3 `properties`

Represents the hotel.

Suggested columns:

```sql
id uuid primary key
slug text unique not null
name text not null
city text not null
state text
country text not null default 'United States'
timezone text not null
room_count integer
created_at timestamptz not null default now()
```

Seed one fictional independent hotel.

Suggested concept:
- 35–50 room boutique inn
- South Haven, Michigan or another plausible leisure destination
- Strong drive-market demand
- Seasonal summer performance
- Chicago as a major feeder market

The property name must come from the database at runtime.

No property switcher is required.

---

## 10.4 `campaigns`

Suggested columns:

```sql
id uuid primary key
property_id uuid not null references properties(id)
name text not null
campaign_type text not null
status text not null
started_at date not null
ended_at date
created_at timestamptz not null default now()
```

Suggested `campaign_type` values:

```text
brand_protection
discovery
metasearch
retargeting
```

Suggested statuses:

```text
active
paused
ended
```

Campaign names must be database-backed.

---

## 10.5 `campaign_daily_metrics`

One row per campaign per day.

Suggested columns:

```sql
id bigint generated always as identity primary key
property_id uuid not null references properties(id)
campaign_id uuid not null references campaigns(id)
metric_date date not null

impressions integer not null default 0
clicks integer not null default 0
website_visits integer not null default 0
ad_spend numeric(12,2) not null default 0

created_at timestamptz not null default now()

unique(campaign_id, metric_date)
```

Integrity expectations:

```text
impressions >= clicks
clicks >= website_visits
all metrics >= 0
ad_spend >= 0
```

Do not store CTR as a source-of-truth column. Derive it.

---

## 10.6 `bookings`

Use event-level bookings rather than one pre-aggregated dashboard number.

Suggested columns:

```sql
id uuid primary key
property_id uuid not null references properties(id)
campaign_id uuid references campaigns(id)

booked_at timestamptz not null
check_in date not null
check_out date not null

booking_value numeric(12,2) not null
room_nights integer not null

guest_city text
guest_region text
guest_country text not null default 'United States'

device text
attributed_to_autumn boolean not null default true
attribution_type text default 'last_touch'

created_at timestamptz not null default now()
```

Possible `device` values:

```text
mobile
desktop
tablet
```

Use `booked_at` for marketing-performance date-range filtering.

Do not use `check_in` as the primary dashboard performance date unless explicitly stated.

Derived:
- booking count = `COUNT(*)`
- booking revenue = `SUM(booking_value)`
- average booking value = `SUM(booking_value) / COUNT(*)`

---

## 10.7 `autumn_actions`

Represents meaningful actions Autumn has taken.

Suggested columns:

```sql
id uuid primary key
property_id uuid not null references properties(id)
campaign_id uuid references campaigns(id)

action_date date not null
action_type text not null
title text not null
description text not null
status text not null

created_at timestamptz not null default now()
```

Suggested statuses:

```text
active
completed
monitoring
```

These records must be fetched from the database.

# 11. Derived Metric Definitions

Create a centralized data/analytics layer. Do not calculate the same metric differently in different components.

## Direct booking revenue

```text
SUM(bookings.booking_value)
WHERE attributed_to_autumn = true
AND booked_at within selected date range
```

## Direct bookings

```text
COUNT(bookings)
WHERE attributed_to_autumn = true
AND booked_at within selected date range
```

## Impressions

```text
SUM(campaign_daily_metrics.impressions)
within selected date range
```

## Ad clicks

```text
SUM(campaign_daily_metrics.clicks)
within selected date range
```

## Website visits from Autumn ads

```text
SUM(campaign_daily_metrics.website_visits)
within selected date range
```

## CTR

```text
clicks / impressions
```

Guard against division by zero.

## Website visitor → booking conversion

```text
attributed bookings / website visits
```

Guard against division by zero.

## Average booking value

```text
booking revenue / booking count
```

## YoY change

For a selected current range, calculate the equivalent dates one year earlier.

```text
(current - prior_year) / prior_year
```

If prior value is zero, display an appropriate non-percentage state rather than Infinity.

## Campaign revenue

Group bookings by `campaign_id` and sum booking value.

## Campaign bookings

Group bookings by `campaign_id` and count.

## Top feeder market

Group attributed bookings by `guest_city` and compare by:
- booking revenue,
- booking count,
- YoY growth.

Default ranking on screen:
- booking revenue descending.

# 12. Seed Data Requirements

## 12.1 Dataset length

Generate **760+ days**.

A reasonable fixed assessment range is approximately:
- late summer 2024 through September 5, 2026.

A fixed deterministic seed is preferable to generating a completely different product every time the script runs.

---

## 12.2 Data must tell a coherent story

Create a believable independent-hotel marketing program.

Suggested story:

### Property
A ~40-room leisure-focused independent boutique hotel in South Haven, Michigan.

### Seasonality
- Strongest demand: May–September
- Peak: June–August
- Shoulder: April, October
- Lower demand: January–February
- Weekend demand higher than weekday demand

### Feeder markets
Example weighted markets:
- Chicago
- Detroit
- Grand Rapids
- Indianapolis
- Milwaukee
- Other Midwest markets

Chicago should plausibly be the largest source.

### Campaign behavior

**Brand Protection**
- lower impressions,
- high CTR,
- high conversion,
- strong booking contribution.

**Discovery & Competitors**
- high impressions,
- lower CTR,
- lower conversion,
- useful new-customer reach.

**Metasearch**
- high-intent traffic,
- good booking conversion,
- strong average booking value.

**Retargeting**
- smaller volume,
- good conversion,
- efficient supporting contribution.

### Improvement story

2026 should be modestly stronger than 2025 overall.

Do not make every metric monotonically improve.

Create:
- normal daily variance,
- seasonal peaks,
- some weaker weeks,
- at least one period where traffic rises faster than bookings,
- at least one market that improves strongly,
- realistic campaign differences.

This supports meaningful insight cards.

---

## 12.3 Generate coherent bookings

Do not independently generate booking revenue as unrelated noise.

Suggested logic:

1. Determine daily campaign impressions.
2. Apply campaign-specific CTR.
3. Derive clicks.
4. Apply click-to-visit rate.
5. Derive website visits.
6. Apply campaign/season-specific booking conversion.
7. Generate booking events.
8. Generate:
   - length of stay,
   - ADR,
   - booking value,
   - market,
   - device,
   - check-in/check-out.
9. Revenue becomes the sum of real generated bookings.

This ensures the journey approximately reconciles.

### Example conceptual model

```text
base campaign demand
× seasonal multiplier
× weekday/weekend multiplier
× year improvement factor
× small deterministic variance
= impressions

impressions × campaign CTR
= clicks

clicks × landing success rate
= website visits

website visits × campaign conversion
= bookings

room nights × ADR
= booking value
```

---

## 12.4 Booking value realism

Avoid every booking being approximately identical.

Generate:
- 1–5 night stays,
- higher ADR in peak summer,
- somewhat higher weekend rates,
- occasional higher-value stays,
- sensible minimum/maximum values.

The result should produce a plausible average booking value, not a suspiciously perfect constant.

If the script needs to clear/reseed demo data, make that behavior explicit and safe for this take-home environment.

# 21. Dynamic Insight Logic — Suggested Implementation

Create a function approximately like:

```ts
generateInsights({
  current,
  comparison,
  campaigns,
  markets
})
```

Return max 3.

Prioritize:

1. Meaningful concern
2. Major revenue/bookings movement
3. Strong market/campaign opportunity

Example pseudo-rules:

```text
IF revenueYoY <= -10%
  => revenue decline insight

IF visitsYoY >= +15% AND conversionYoY <= -10% relative
  => traffic up / conversion down concern

IF revenueYoY >= +10%
  => revenue growth insight

IF bookingCountYoY >= +10%
  => booking growth insight

IF topMarket revenue growth >= +20%
  => market growth insight

IF topCampaign revenue share >= 40%
  => strongest campaign insight

ELSE
  => steady performance insight
```

Do not overfit thresholds. The goal is meaningful communication, not an "AI insights engine."

# 28. Final Product Rationale

The redesign should demonstrate the following reasoning in the follow-up interview:

### Why revenue and bookings come first
They directly answer whether Autumn is producing business value.

### Why impressions and website visits remain
They explain how marketing created the outcome, but they are combined into a journey rather than presented as equally important standalone cards.

### Why CTR is demoted
CTR is a useful marketing diagnostic, but a hotel owner cares more about whether visitors become bookings and revenue.

### Why Total Booking Value is removed as a separate card
It duplicates the revenue already present in Autumn Results.

### Why Device Summary is removed from the overview
It is diagnostic, not executive-level. It only deserves prominence when device behavior materially explains a result.

### Why the second screen is booking performance instead of generic website traffic
It naturally answers the question created by the main dashboard:
> "Autumn generated this revenue — what actually drove it?"

### Why YoY is emphasized
Hotels are seasonal. Comparing a summer month with the prior winter month can be misleading. Same-period-last-year comparison gives the owner better context.

### Why insights matter
The user should not have to interpret raw numbers. Autumn should translate data into meaning.

### Why "What Autumn is doing" matters
The user wants confidence that Autumn is actively managing performance, not merely reporting it.

### Why the data model is event/fact based
The assignment is explicitly testing whether the product is real rather than a hardcoded prototype. Underlying campaign metrics and booking events make every top-level metric traceable and dynamically recomputable.
